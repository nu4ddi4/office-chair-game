# 버전 관리

`godot/prototype/version.json`의 `version`은 다음 정식 버전 목표(`X.Y.Z`)다. 실제 배포 버전은 CI에서 정하고 소스에 자동 커밋하지 않는다.

| 브랜치 | 자동 릴리스 |
| --- | --- |
| `beta` | 목표 또는 최신 정식 다음 버전 중 큰 쪽의 `X.Y.Z-beta.N`. 이미 공개한 beta 목표도 유지하며 순번 증가 |
| `main` | 목표 버전 `X.Y.Z`. 이미 배포한 버전이면 최신 정식 버전의 patch 증가 |
| 개발 브랜치·PR | 게시하지 않음 |

예: `0.8.0-beta.1` → `0.8.0-beta.2` → main 승격 시 `0.8.0`. 이후 beta는 `0.8.1-beta.1`부터 시작하므로 정식보다 낮은 기반 버전의 beta를 계속 발급하지 않는다. 소스 목표를 `0.9.0`으로 높이면 그 목표를 사용한다. 같은 목표에서 beta 순번은 최대 998이다.

태그·릴리스 이름은 `SecurityLab-<실제 버전>`으로 통일한다. 릴리스 파일은 EXE·설치 파일·APK 그대로이며 zip으로 감싸지 않는다. 앱 내부 버전·파일명·설치 프로그램·업데이트 manifest에도 같은 버전을 넣는다. Android versionCode는 정식 버전과 beta 순번을 함께 반영하며 같은 목표의 정식 버전이 beta보다 크다.

`main`·`beta` push마다 검사 후 배포한다. 문서 변경도 포함한다. 실패한 실행은 게시하지 않으며 이미 공개한 파일·태그는 덮어쓰지 않는다. 같은 커밋을 재실행하면 기존 버전을 재사용한다. 일부 업로드가 실패한 초안은 재시도할 수 있고, 채널 반영 실패는 공개한 파일을 유지한 채 복구한다.

기존 목표 정식 버전에 APK가 빠져 있고 게임 소스가 동일하면, Android 검사 후 해당 버전에 APK·개별 체크섬만 추가할 수 있다. 기존 Windows 파일·전체 체크섬·태그는 보존하고 버전을 올리지 않는다. 이후 일반 변경은 위 자동 버전 규칙을 따른다.

Windows 업데이트 채널은 `beta-channel-beta` / `beta-channel-stable`로 분리한다. 버전 파일 게시 완료 후에만 채널을 반영한다. 게임의 업데이트는 알림과 사용자 동의 후에 진행한다.

현재 소스 목표가 이미 배포한 정식보다 낮더라도 실제 beta 목표는 최신 정식의 다음 버전으로 올린다. 앱은 선택한 정식 또는 beta 채널만 확인하며 현재 버전보다 낮은 릴리스로 전환하지 않는다. main과 beta 모두 Windows·Android를 배포하며, 출시 전 APK는 같은 공용 개발 키로 서명한다.
